### 5b. Anonymous-demo "don't actually store votes" — design discussed, nothing filed, nothing implemented
User wants: when an anonymous (not-logged-in) visitor uses a `demo`-access-policy
conversation, their votes/statements/arguments should **not** be persisted to the DB
or forwarded to Particiapi/Polis at all — but the UI should behave identically (same
animations, same button states) as if they were. Also wants a clear banner at the top
of the page for anonymous demo sessions saying so. Critically, they want this to
**never need re-syncing by hand** when the real conversation code changes later.

This reverses the *current, deliberate* design from #293: today, anonymous demo
visitors get a real synthetic guest `Participant` and their votes/statements/arguments
genuinely are recorded (`_ensure_demo_participation`, `app.py:1279-1360`, docstring:
*"A demo is a genuine demonstration conversation that records as usual (#293)"*).

I recommended (but did not get confirmation on) an approach: **mock at the
server-side proxy/route layer**, not client-side. Concretely: `_proxy_to_particiapi`,
`conversation_statement_new`, `argument_submit`/`argument_skip`, `phase6_vote` each
get an early branch — *if this is an anonymous demo session, synthesize a
plausible-shaped response and return, skip every DB write / upstream call* — so the
interactive JS in `conversation.html` needs **zero** changes and can never drift out
of sync, because it doesn't know the difference.

**Open problem I flagged and never got resolved**: if writes are fully mocked, what
happens to any later "your personal results" / clustering view that would normally
include the anonymous visitor's own (now unsaved) input? Either that needs its own
mocking too (bigger surface), or it needs to visibly exclude/caveat the anonymous
visitor's results specifically. I asked whether to scope this now or punt as a
follow-up decision — no answer.

**Next step**: this needs a product decision before it can become a scoped issue —
at minimum, resolve the read-side question above. Don't start implementing without
that; the design is sound but incomplete.

## 7. Things learned that aren't obvious from the diff

- **The `claude/issue-recording-srqci0` branch's earlier PR (#297) got merged into
  `main` mid-session, out from under me.** When I later committed the a11y fix
  (`67cdc95`, originally `a436093` before the rebase) and pushed, git printed
  `[new branch]` instead of a normal fast-forward — that was the tell. The remote
  branch had been deleted after the merge (normal GitHub post-merge cleanup), so the
  push silently recreated it from stale, already-merged history instead of updating
  it. **Lesson for next time**: after any push that reports `[new branch]` on a
  branch you know already existed, immediately check whether its PR merged
  (`pull_request_read`) rather than assuming the push just worked. Fixed here via
  `git checkout -B claude/issue-recording-srqci0 origin/main && git cherry-pick
  a436093`, re-ran the full suite against the new base, then
  `git push --force-with-lease`. `main` had moved by 20 commits (other unrelated
  merged PRs — #282, #281, #275, etc.) during this session; none of that is mine to
  account for, just noting the branch needed a real rebase, not a trivial one.
- **`pr-check` is a config file, not a running skill, in this environment.**
  `.claude/pr-check.json` is per-project *config* for a `pr-check` skill that isn't
  actually installed/enabled in this session (confirmed via `ListSkills`). When asked
  to run it, I approximated it by hand using the config's `test_command`, `scope`,
  and `sensitive_patterns` fields directly — worked fine, but if the next session has
  the real skill (per the agent-tooling 0.15.0 note in §1), prefer that.
  The config's `e2e_skill`/`staging_skill` (`local-e2e`, `staging-chrome-test`) were
  never available either — that's a real coverage gap for anything touching
  `RUNTIME`-scoped files (per the config: `conversation.html`, `reveal.html`,
  `polis_admin.py`), including `67cdc95`. Nobody actually browser-tested that fix.
- **No Docker daemon and no outbound access to `wiki-polis.toolforge.org`** in this
  sandbox (egress blocked) — any future "let's just check production" instinct will
  hit a wall immediately; don't waste time trying, go straight to code-reading plus
  asking the user to check directly.
- **The demo-mode design (#293) is more load-bearing than it first looks.** Multiple
  threads this session (5b, 5c, plus the earlier `fork.html`/`home.html` split
  research) all converge on `_ensure_demo_participation` / `_demo_bound_conversation_id`
  / `_demo_proxy_allowed` (`app.py:1247-1360`, `1638-1668`) as the actual center of
  gravity for "how does anonymous trial participation work." Anyone touching demo
  behavior should read that whole block first, not just the piece their task touches.
